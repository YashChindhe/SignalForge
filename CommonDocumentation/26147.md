## Background

The raw data for analysis of signal collected off the air typically range from few **KHz to GHz bands**. The analysis is being carried out **manually** to identify the signal parameters and the resultant data is then utilised for processing signals in the designated sensors. This data is often insufficient for fine-grain analysis for parameter extraction such as **modulation type, sampling rate, FEC, interleaving**, etc. This creates a need for **advanced data processing** to extract the observation data.

---

## Description

The terrestrial signals received from various sources include data in **HF, VHF and UHF bands**. The raw data is collected in the form of **.wav** or **.IQ** format to retain the characteristics of the waveform.

The analysis of signals is primarily dependent on the basic characteristics of data points selected during recording of these signals. Since the data points are recorded from **different sensors and different locations**, the parameters may vary. Therefore, the data available for analysis is often **insufficient** to clearly identify fine details such as:

- Sampling rate
- Modulation type
- Interleaving
- FEC (Forward Error Correction)

This limitation reduces the **accuracy and confidence** of interpretation and data analysis that require detailed information.

The data saved as **.IQ** and **.wav** have different parameters and therefore they store the raw information in **different formats**. These files have to be processed in different ways for signal analysis to extract signal parameters.

The problem can be addressed using advanced models such as **GNU Radio, Python, C++** to enhance the parameter extraction capability and more information-rich inputs. The spectral relationship from training data containing both .IQ and .wav formats can be utilised for identifying signal parameters and carry out deeper analysis. **The expected solution should be able to demodulate signals.**

## 1. Detailed Explanation of the Proposed Solution

### What is SignalForge?

**SignalForge** is a desktop GUI application that takes **.IQ** and **.wav** files as input and automates the signal analysis workflow — parameter extraction, visualization, demodulation, and decoding — replacing the current manual process with a structured, repeatable pipeline.

### Core Design Principle: Layered Automation

Rather than promising a single magic button, SignalForge is designed as a **guided automation tool** — it automates what can be reliably automated, and provides visual tools + manual overrides where full automation is not yet reliable.

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  STAGE 1    │────▶│  STAGE 2     │────▶│  STAGE 3     │────▶│  STAGE 4     │────▶│  STAGE 5     │
│  File Load  │     │  Visualize & │     │  Demodulate  │     │  De-interl.  │     │  FEC Decode  │
│  & Parse    │     │  Param ID    │     │              │     │  (with known │     │  & Bit View  │
│             │     │              │     │              │     │   params)    │     │              │
└─────────────┘     └──────────────┘     └──────────────┘     └──────────────┘     └──────────────┘
   FULLY AUTO          AUTO + GUI           AUTO-SELECT          USER-ASSISTED         LIBRARY-BASED
```

### How Each Stage Actually Works

**Stage 1 — File Ingest (Fully Automated)**

- **.wav files**: `scipy.io.wavfile.read()` gives us PCM samples + sample rate directly from the file header. If the signal is real-valued, we apply a Hilbert transform to get the analytic (complex) signal.
- **.IQ files**: These have no standard header. The user selects the sample format from a dropdown (float32, int16, complex64, interleaved vs. non-interleaved). We provide a "preview" that shows the first few hundred samples so the user can verify the format looks correct before proceeding.
- Output: A **NumPy complex64 array** + a metadata dict (sample rate, duration, number of samples).

> **Why not auto-detect .IQ format?** Because a stream of raw bytes has no reliable way to distinguish float32 from int16 without context. Attempting "auto-detection" gives false confidence. A simple dropdown with preview is honest and fast.

**Stage 2 — Signal Parameter Identification**

- **Sampling Frequency**: For .wav, it's in the header (done). For .IQ, the user provides it (since .IQ files don't store sample rate). The GUI displays it prominently.
- **Spectral Analysis**: FFT-based power spectral density (Welch method, `scipy.signal.welch`). Displayed as spectrum plot + waterfall/spectrogram. These are standard DSP operations — no ML needed, totally reliable.
- **Bandwidth Estimation**: −3 dB or −10 dB bandwidth from the PSD. Simple thresholding on the spectral envelope.
- **Modulation Classification**: This is where we use ML, but **realistically**:
  - **Primary approach**: Extract **6 statistical features** from the signal — standard deviation of instantaneous amplitude, phase, frequency; kurtosis of amplitude; max spectral density; zero-crossing rate. Feed these into a **Random Forest classifier** trained on the RadioML 2018.01A dataset (pre-hackathon).
  - **Why Random Forest over CNN?** A Random Forest on hand-crafted features is trainable in minutes on a laptop, has no GPU dependency, gives interpretable results, and achieves **~75-80% accuracy at SNR ≥ 5 dB** on common modulation types (BPSK, QPSK, FSK, AM, FM). This is honest and demonstrable. A CNN+LSTM sounds impressive on slides but is fragile to deploy correctly under hackathon pressure.
  - **Stretch goal**: If time permits, we also train a simple 1D-CNN on raw IQ samples and use it as a secondary classifier. But the Random Forest is the workhorse.
  - Supported types (realistic): **BPSK, QPSK, 2FSK, 4FSK, AM-DSB, FM, 8PSK** — these are the ones where the classifier is most reliable.
- **Constellation Diagram**: Scatter plot of I vs Q after timing recovery. This is a visualization, not a classification — it helps the analyst visually confirm the ML result.

**Stage 3 — Demodulation**

- **FSK (2FSK, 4FSK)**: Frequency discriminator (instantaneous frequency via `np.diff(np.unwrap(np.angle(signal)))`) → low-pass filter → symbol timing recovery using zero-crossing detection → bit slicer. This is textbook DSP and fully implementable.
- **BPSK / QPSK**: Costas loop for carrier recovery (standard implementation, ~100 lines of Python) → RRC matched filter (`commpy.filters.rrcosfilter`) → Mueller & Müller timing recovery → hard-decision mapping. BPSK is straightforward; QPSK adds phase ambiguity handling.
- **QAM (16-QAM)**: Listed as a **stretch goal**. QAM requires blind equalization (CMA algorithm) which is significantly harder to get right. If we get here, it'll be a basic CMA + decision-directed approach, but we won't promise it in the demo.
- Output: **Bit stream** (hard decisions) + **constellation plot** (for visual verification).

**Stage 4 — De-Interleaving**

- **Honest truth**: Blind detection of interleaving type and parameters from a raw bit stream is an **open research problem**. We will NOT claim to auto-detect it.
- **What we actually build**: A de-interleaving module where the user **selects the type** (Block, Convolutional, Diagonal, Pseudo-Random) and **inputs the parameters** (block size, depth, span, LFSR polynomial). The tool then applies the inverse operation.
  - Block: Matrix transpose — trivial (`numpy.reshape + transpose`).
  - Convolutional: Shift-register implementation — straightforward.
  - Diagonal: Row-column reversal — similar to block.
  - Pseudo-Random: Requires LFSR polynomial — user provides it, we apply inverse permutation.
- **Why user-assisted?** Because getting this wrong silently corrupts the entire downstream chain. It's better to be correct with user input than wrong with false automation.

**Stage 5 — FEC Decoding & Bit Stream Viewer**

- **Viterbi Decoder** (Convolutional Codes): Using `commpy.channelcoding.convcode`. User selects constraint length (K=3 to 7) and code rate (1/2, 1/3). This library function is well-tested and works reliably.
- **Reed-Solomon Decoder**: Using `commpy` or `reedsolo` Python library. User provides (n, k) parameters. Straightforward.
- **LDPC**: **Stretch goal only**. Belief propagation is complex and `commpy`'s LDPC support is limited. We'll attempt it if time allows.
- **Concatenated Codes**: **Future scope**. This requires chaining RS + Viterbi in the correct order with the correct parameters — doable but not in 36 hours alongside everything else.
- **Bit Stream Viewer**: Display decoded bits as hex dump with search capability. If sync words are known, the user can input them and we'll highlight matches using `numpy.correlate`. This is simple cross-correlation — fully achievable.

### How It Addresses the Problem

| Current Problem                                       | SignalForge Solution                                         |
| ----------------------------------------------------- | ------------------------------------------------------------ |
| Manual analysis — slow, error-prone                   | Automated pipeline with ML classification + visual tools     |
| .IQ and .wav handled separately                       | Unified ingest — both formats normalize to complex baseband  |
| Insufficient data for fine-grain parameter extraction | Spectral analysis + statistical feature extraction           |
| No demodulation capability in current workflow        | Built-in demodulators for FSK and PSK                        |
| No automated FEC / de-interleaving                    | Library-based decoders (Viterbi, RS) with user-guided params |
| No correlation for header/payload identification      | Hex bit viewer with sync word search                         |

### Innovation & Uniqueness

1. **ML-Assisted (Not ML-Dependent)** — The classifier suggests modulation type; the constellation + waterfall let the analyst verify. No black-box trust required.
2. **Unified .IQ / .wav Pipeline** — One tool for both formats. No switching between applications.
3. **Guided Automation** — Automates the automatable (spectral analysis, feature extraction, demodulation). User-assists where blind automation is unreliable (de-interleaving params, FEC config). This is honest and practical.
4. **Rich Visualization** — Spectrum, waterfall, constellation, and bit stream views in one window. This alone saves significant time vs. current manual workflow.
5. **Fully Offline** — No internet, no cloud, no external API. Runs on a standalone laptop. Critical for NTRO's operational security.
6. **Open-Source Stack** — No vendor lock-in. NTRO can extend it internally with classified modules.

### Pre-Hackathon Preparation (What We Do Before Day 1)

This is critical — the ML model must be trained before the hackathon:

1. **Download RadioML 2018.01A** dataset (~2.5 GB HDF5 file)
2. **Extract 6 statistical features** per signal sample:
   - `σ(|a(t)|)` — std dev of instantaneous amplitude
   - `κ(|a(t)|)` — kurtosis of instantaneous amplitude
   - `σ(φ(t))` — std dev of instantaneous phase
   - `σ(f(t))` — std dev of instantaneous frequency
   - `γ_max` — max value of spectral power density
   - `R_zc` — zero-crossing rate
3. **Train Random Forest** (100 trees, max_depth=20) → `joblib.dump(model, 'rf_classifier.pkl')` — this takes ~5 minutes on a laptop
4. **Validate**: Test on held-out set, record confusion matrix. Honest expected accuracy:

| SNR Range  | Expected Accuracy | Notes                                      |
| ---------- | ----------------- | ------------------------------------------ |
| ≥ 10 dB    | ~80-85%           | Good separation between modulation types   |
| 5 to 10 dB | ~70-75%           | FSK/PSK distinguishable, QAM variants blur |
| 0 to 5 dB  | ~55-65%           | AM/FM still OK, digital mods get confused  |
| < 0 dB     | ~35-45%           | Near random — this is expected             |

> These are honest numbers. Published CNN papers claim 90%+ but that's on clean synthetic data with perfect timing. On real-world signals, expect lower. Our GUI's constellation and waterfall views let the analyst override when ML is uncertain.

## 4. Feasibility Analysis

### Why This Is Achievable

| Claim                          | Evidence                                                                        |
| ------------------------------ | ------------------------------------------------------------------------------- |
| File parsing works             | `scipy.io.wavfile` and `np.fromfile` are one-liner functions                    |
| Spectral plots work            | `scipy.signal.welch` + `matplotlib` — thousands of tutorials exist              |
| Random Forest classifier works | scikit-learn RF on RadioML is a well-documented approach in academic literature |
| FSK demodulation works         | Frequency discriminator is <50 lines of NumPy code                              |

| Viterbi decoder works          | `commpy.channelcoding.viterbi_decode` — one function call                       |
| PyQt6 GUI works                | Standard Python desktop GUI, team has prior experience                          |

### Potential Challenges & Honest Risks

| Challenge                                   | Risk   | Our Approach                                                         |
| ------------------------------------------- | ------ | -------------------------------------------------------------------- |
| ML classifier underperforms on real signals | High   | GUI shows confidence score + constellation. User can override.       |
| .IQ format guessing is unreliable           | High   | **We don't guess.** User selects from dropdown. Honest > clever.     |
| Timing recovery (symbol sync) is fragile    | Medium | Use Gardner/M&M with manual symbol rate input as fallback            |
| De-interleaving params unknown              | High   | User-provided params. We implement the math, not the detection.      |
| FEC params unknown                          | High   | User-provided params. Viterbi/RS work perfectly with correct params. |
| GUI integration takes longer than expected  | Medium | GUI track starts day 1. Backend and GUI developed in parallel.       |
| Large .IQ files (>1 GB) cause memory issues | Low    | Process in chunks. Load only visible window into memory.             |

### What We Will NOT Claim

Being upfront about limitations builds credibility with NTRO judges:

- ❌ We do NOT auto-detect .IQ file format — user selects it
- ❌ We do NOT auto-detect interleaving type/params — user provides them
- ❌ We do NOT auto-detect FEC code parameters — user selects them
- ❌ We do NOT claim 90%+ classification accuracy — honest range is 70-85% at reasonable SNR
- ❌ We do NOT handle QAM blind equalization in the MVP — it's a stretch goal
- ❌ We do NOT claim real-time processing of live SDR streams — this is file-based analysis only

> **Why list limitations?** Because NTRO is a technical org. They will ask hard questions. Having clear, honest answers about what you can and can't do is far more impressive than vague claims of "AI-powered everything."

## 5. Impact & Benefits

### Impact on NTRO's Workflow

- **Faster turnaround**: Spectrum analysis + modulation ID that currently takes an analyst 30-60 minutes is done in **under 2 minutes** (file load + auto-classify + view plots).
- **Reduced human error**: The ML classifier + constellation plot together give a reliable modulation identification. Analyst confirms visually rather than guessing from raw data.
- **Analyst empowerment, not replacement**: The tool handles the tedious parts (FFT, timing recovery, Viterbi decoding). The analyst focuses on interpretation — what does this signal mean, who's transmitting, what protocol is it?
- **Reproducible results**: Same file → same output every time. No more "different analysts get different results" problem.
- **Training tool**: New analysts can learn signal analysis by loading known signals and observing the classification + demodulation process step by step.
